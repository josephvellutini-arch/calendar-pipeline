The Calendar Pipeline

A small system of scheduled agents, a database, and a real calendar — built to hold a demanding, irregular schedule without ever quietly getting it wrong.

Why this exists

A schedule that doesn't fit a normal calendar app

I'm doing independent research and applying to PhD programs while also working an irregular shift job, and none of that runs on a tidy 9-to-5. Some mornings start at 4am. Some days need two hours of uninterrupted deep work and nothing else touches them. A recurring reading habit needs to survive weeks without turning into guilt. A read-later list needs an honest way to say "not right now" instead of silently growing forever.

A normal calendar app can hold fixed events fine. What it can't do is reason — decide what today should look like given yesterday's leftovers, this week's deadlines, and a work shift that starts at an hour most planning tools don't expect. That reasoning needed to happen somewhere, on a schedule, without me having to trigger it by hand every morning.

So the actual thing I built isn't a calendar. It's a small pipeline of agents that read my real calendars and inbox, propose a plan, and only ever touch the live calendar once I've said yes.

Philosophy

A few rules the whole system answers to

None of these were decided up front. Each one is the direct result of something going wrong once, in a small, low-stakes way, and getting fixed before it became a habit of not trusting the system.

Draft, never assume

Every agent that plans a day, a week, or a month is only ever allowed to write a draft. Nothing reaches the real calendar until a human looks at it and explicitly approves it. An agent that's wrong about your schedule is a nuisance; an agent that's wrong and silently commits to your calendar is a liability. The fix is structural, not a prompt asking it to be careful.

No memory, no drift

Each scheduled run starts from zero — no memory of yesterday's run, no accumulated state to get subtly wrong over time. Everything it needs, it re-reads fresh from the same sources every time: the calendar, the inbox, the database. A bug in yesterday's output can't compound into next week's, because there's nothing to compound; everything is recomputed from the same ground truth every single time.

One place holds the truth

The database is the real record. The calendar is a projection of it — created only after approval, and only ever added to, never silently edited or deleted by anything automated. If the calendar and the database ever disagree, the database wins, because it's the only thing every agent actually reads and writes directly.

"Not right now" has to be a real option

Early on, a recurring to-do carried forward unresolved for over three weeks straight — not because it wasn't important, just because the only two states available were "done" or "still open," and there was no way to say "not today, ask me again later" without it either nagging forever or getting deleted and losing its history. The fix was a proper three-state system: doing, done, and paused-with-an-optional-return-date. Deferring something on purpose is not the same as ignoring it, and the system needed to know the difference.

Prefer the platform's own reliable channel over a clever custom one

The system went through two different custom notification setups before landing on the obvious answer: if you need someone to notice something changed, use the notification system already built into the app they check constantly — in this case, letting a calendar app's own native reminder do the job — rather than routing around it through a separate push service that can silently fail with no visible error. The fanciest bridge is still worse than the boring default that's already proven reliable.

How it works

Four small agents, one shared record

The architecture is intentionally boring. A handful of scheduled agents run on fixed timers, read from the same calendars and the same database every time, and write drafts. A human approval step is the only thing that ever lets a draft become a real event.

The database also holds an open-ended task list with three states — doing, paused (with an optional return date), and done — so anything discretionary has a real way to be deferred on purpose instead of nagging forever or vanishing without a trace.

Notification is the one place where the design changed the most. The first version tried a custom push service; it silently failed on scheduled runs more than once with no visible error. The current version has a drafting agent create one small calendar event whose only job is to trigger the calendar app's own native reminder — the same reliable notification you already get for any other event — and a cleanup pass removes it once that plan's been reviewed. No custom relay, no new failure mode.

Lessons

What actually mattered, building this

01

A sandboxed agent's network is smaller than you'd guess

Scheduled cloud agents often run with a fixed outbound network allowlist — a handful of known hosts, nothing else. A clever webhook or push service you'd reach for locally may simply be unreachable from that environment, and it fails quietly rather than with an obvious error. Check what's actually reachable before designing around a service you haven't tested from inside the sandbox itself.

02

"Success" isn't the same as "delivered"

A notification call can return a clean success response and still never reach the device it was meant for. If a channel matters, verify delivery end to end at least once — don't trust the API response alone.

03

Default reminders assume the future

A calendar event with a default "30 minutes before" reminder never fires if the event starts right now — that trigger point is already in the past by the time the event exists. Any reminder meant to be immediate needs an explicit override, not the default.

04

Keep a changelog for systems that build themselves over time

A system that grows in small increments over weeks is easy to lose track of — which fix superseded which, and why. A short dated history, kept alongside the system itself, turns "wait, didn't we already try that" into a five-second lookup.
